# LLMの即興対話で研修を進める

本番の中心は、相手の発言を受けてLLMが返答と身ぶりを生成する対話である。発表シナリオは、舞台・役割・場面の目的を共有するために使う。

実機運用はLAN接続を使用し、未接続時のマイク・チャット試験は明示的な `-Offline` のローカルモードで行う。どちらもURLは8770を使用する。ユーザー指示で仮想R1を凍結し、仮想器と仮想パネルは停止した。保存データは維持し、明示的な再開指示まで仮想器の起動・問い合わせ・変更・仮想受入テストは行わない。

今回の設定は `local_tools/r1_startup.json` に保存し、リポジトリのルートで `pwsh -NoProfile -ExecutionPolicy Bypass -File .\local_tools\start_r1.ps1` を実行すると、LAN接続待ち→対象Ethernetの設定確認→R1応答確認→実機パネル起動→ブラウザ表示まで進む。起動完了には実機のFSM読取成功も必要。LAN未接続なら待機後に終了する。2026-11-15に実機の通し再起動と、通常コマンドの再実行で二重起動しないことを確認した。

### 通信復旧後の状態監視と停止再確認

LowStateの新しい有効データが1秒以上採用されなければ、同じ受信スレッドでLowState readerだけを作り直す。再接続後はCRC正常で進行するtickを3件以上、0.2秒以上確認してから有効にする。古いキャッシュ1件や、旧readerの処理で鮮度を復活させない。受信世代が変われば静止観測の窓と確認履歴も区別する。受信・採用時刻、tick、再接続回数は状態APIのbody.monitorで確認できる。

実機起動は停止再確認ロック付きとし、「停止を再確認」のゼロ速度送信後、新しい同じ受信世代のデータで0.5秒の静止を観測して解除する。停止未確認の旧パネルを明示的な `-Restart` で置き換えるときも、このロックを引き継ぐ。通信復旧だけでは停止未確認を解除せず、歩行を自動再開しない。ネイティブのReadが完全に停止して終了できない場合は、同時に新readerを重ねずロックを維持する。

2026-11-15の検証では429件のPythonテストと、起動スクリプト53ケース・157項目が通過。別の読み取り専用プロセスで連番判定を一時的に進まなくし、実機のLowState readerを自動再作成して受信世代1→2へ復旧することを確認した。LANや実機の再起動を意図的に起こした試験ではない。実機パネルの再起動時に停止ロックが残ること、その後ゼロ速度1回と新しい静止観測で解除できることも確認した（`logs/feedback_recovery_acceptance_*.json`）。応答127と目視確認が必要な扱いは維持し、歩行試験は実施していない。

### 手動ボタンを押している間の歩行

方向ボタンは押している間だけ速度指令を更新する。マウス・タッチ・Space/Enterに対応し、離す、ボタン外へ移動、フォーカス喪失、画面非表示でゼロ速度を送る。ユーザーの「3倍ほど」の指定により、手動の前後左右を0.3から0.9 m/sに変更した。旋回は0.3→0.9→1.8 rad/sへユーザー指定で変更し、会話の単発指令の設定は維持する。手動速度は `--hold-linear-speed`（アプリ側上限0.9）と `--hold-yaw-speed`（アプリ側上限1.8）で指定できる。この設定は機体のメーカー保証上限や実測速度ではない。

ブラウザーは0.2秒ごとに押下を更新し、サーバーは更新が0.75秒途切れると後続の速度更新を止めてゼロ速度を送る。ネイティブ指令のdurationは2秒、更新間隔は0.3秒である。操作のトークンと停止世代番号により、解除済み・停止前・再起動前の遅延リクエストで動作を再開しない。停止後の関節確認が終わるまで他の会話・腕・起立と排他にする。応答127や通信断時に、実際の停止を保証した意味ではない。

この改修では実機への歩行試験指令を送らず、偽物のSDK・時計・ブラウザー環境で継続更新、解除、通信更新期限切れ、状態異常、遅延リクエストを検証した。新しい押下操作の実機での動作・停止は目視確認が必要。

### マイク開始エラーへの対応

Nothing Earの通話開始でWindows WDM-KSのPortAudio -9999が出た。起動時の固定デバイス番号を避け、`--mic-device "Nothing Ear (3a)"` と指定し、通話・単発録音の開始時に同じ物理機器のWASAPI入力を選ぶ。別の物理マイクへ黙って切り替えない。

PC上ではWASAPIの16kHz入力開始と入力データの到着を確認し、修正後のVoiceCallでも認識を無効にした入力開始が成功した。音声の保存や外部送信、R1の発話は行っていない。パネルを再読み込みして「通話を開始」で再開する。選択した機器名と音声方式は通話欄へ表示する。

その後、WASAPI選択済みでもヘッドセットを外すとWindowsドライバーの開始エラーが出ることを確認した。指定入力が使えない間は通話を接続待ちにし、同じNothing Earへの入力再接続を1秒ごとに試す。入力ストリーム停止や3秒のデータ途絶も待機へ移す。接続待ち中は認識せず、切断前の未処理音声や応答を復帰後に再利用しない。「通話を終了」で再試行も取り消す。起動時に機器が見つからなくてもPC本体のマイクへ切り替えない。

装着センサーには接続していないため、これはWindowsの入力切断・エラー・途絶を検出する処理である。片耳を外しても入力が正常に続く機器状態では、装着の有無そのものは判断しない。再接続・停止・古い音声の取り消しは偽物の入力ストリームで検証し、PCの実入力では認識を無効にした接続開始まで確認した。

同じ入力を新規プロセスで開くと取得できる一方、長時間動作中のパネルではWASAPI選択済みでも開始に失敗する例が出た。そのためLAN実機モードでは、失敗した入力を閉じた後に、このPythonプロセスのPortAudioを再初期化してから同じ機器を再列挙する。別のマイクやWindows設定へは変更しない。マイクの処理は一つずつ実行し、再初期化中に単発録音を重ねない。初期化参照数と入力の終了状態を検査し、確認できない場合は接続待ちに留める。[PortAudioの初期化・終了仕様](https://portaudio.com/docs/v19-doxydocs/portaudio_8h.html) に従い、実装はインストール済みsounddeviceの内部関数へ依存する。

2026-11-15 10:14、LAN実機パネルで開始時エラーから約2秒後に同じNothing Earの入力へ復帰し、`input_ready=true`・聞き取り中・入力レベルの変化を確認した。実音声「こんにちは聞こえますか マイクでしゃべっています」を認識し、GPTの返答と手振り指令まで記録。次の音声も認識して返答した。実際にイヤホンを外して装着し直す往復の確認は別途必要であり、全てのBluetooth状態からの復旧を保証した意味ではない。修正を含む406テストと、オフラインUI5ケースが通過。

### 本体音量と送信前音声の増幅

本体音量は100。ユーザーの追加指定「音声をもう2倍」により、送信前PCMの設定を `--gain 6.0206` から `--gain 12.0412` へ変更した。増幅係数は2から4へ増え、小さい波形は元の約4倍になる。既存のソフトリミッターで大きな波形を丸め、16ビットの数値上限を超えない。聴感上の音量や既に上限近くの波形が正確に2倍になる意味ではない。起動スクリプトも同じ設定を使用する。

### 仰向けからの起立

パネルを再読み込みし、「脱力からの起立」で現在の姿勢を選び、準備確認をチェックして「仰向けから起立」を押す。実機は仰向けで、コントローラー担当者・周囲2m以上の空間・スタッフの許可を確認した場合だけ使う。チャットでは `仰向けで準備確認済み、起立して` と明示する。「起立して」だけ、姿勢不明、準備未確認、認識が不確かな音声では実行しない。吊り下げは対象外。

既存の高レベル手順0→1→4→701→811を使い、各指令の応答0と状態の到達を検査する。すでに811なら起立を重ねず、701なら現在の起き上がりを監視する。LLMの自由なgesture選択には追加していない。中断は後続指令の取り消しであり、開始済みの機体の起き上がりを即時停止する保証ではない。失敗時に自動で脱力や寝る状態へ戻さない。

2026-11-15に実機で起立を確認し、担当者が「立ち上がり、安定して立っている」と目視確認した。初回は4への指令後の読取エラーで止まり、読取のみで4を3回確認してから701へ再開した。記録は `logs/r1_stand_physical_20261115_091903.json` と `logs/r1_stand_physical_20261115_091951.json`。以後のコードは読取例外だけを最大3回再試行し、有効な新しい状態読取が得られなければ次の指令を送らない。指令エラーは再送しない。修正後の起立を繰り返す実機試験は行っていない。

このPCのEthernetには別用途のIPv4もあり、アダプター名だけではDDSが別の送信元を選んだ。起動には `-i Ethernet --dds-address 192.168.123.164 --port 8770` を使う。プロセス内のDDS設定だけで送信元を指定し、SDKファイルや別用途のIPを変更しない。指定方法は [Cyclone DDSの公式設定仕様](https://cyclonedds.io/docs/cyclonedds/latest/config/config_file_reference.html) に従う。状態APIの `connection_kind=robot` と `dds_address` も確認する。

`scenarios/live_training_world.json` は世界設定の構造化資料、`scenarios/live_training_context.txt` は教材として読み込める本文である。どちらも固定台詞や動作コマンド列を持たず、シナリオランナーへ渡す実行ファイルではない。研修の進め方は「説明しながら実演し、その後は新人に聞き、返答に合わせて教える」を基本にする。

## 同じ人格の中で扱う3領域

| 話題 | LLMが考える範囲 | 保つもの |
|---|---|---|
| 架空作業 | 作業例、荷物や製品、理由、小話、ユーモラスな返答を創作できる | A=移動、B=停止、会話中に合意した設定との整合 |
| 現実のR1の内部実装 | コード・技術事実集・検証記録から、質問に関係する事実を説明する | 根拠のない仕様を作らず、不明点を不明とする。公開mainと作業ツリーを区別する |
| 存在意義 | 質問や言語に合う自然な表現を生成する | 新人に機械操作を教え、操作ミスによる事故を防ぐ目的と、AI・プログラム・実行条件の役割 |

架空の機械についての質問に「仕組み」という語があっても、それだけで現実のR1の技術質問とは扱わない。反対に、架空の設定を理由に、現実のR1にない機能を実装済みと説明しない。

技術的な誤答を出さない方針は、単に指示文を書いただけで達成したとは扱わない。根拠、不明時の応答、日英の質問例を評価し、未確認の性能を区別する。

## 対話と動作の使い方

会話パネルで世界設定の本文を研修資料として読み込み、文字または音声で話しかける。新人役は用意した台詞を読む必要はなく、その場で質問や勘違いを表現する。プレゼンターも、場面情報や残り時間を合図として伝える。

研修では次の流れを使う。これは各段階の目的であり、読み上げる台詞の一覧ではない。

1. **説明しながら実演**：R1が一つの作業の目的と手順を短く説明し、発話の意味に合う動作で見本を示す。
2. **一つ質問して待つ**：新人に手順を自分の言葉で話してもらうか、不安な点を一つ尋ねる。新人が答えるまで次へ進まない。
3. **返答に合わせて補足・再実演**：合っている点を伝え、勘違いは理由とともに補足する。必要なら別の例や見本動作に戻る。
4. **再確認して続ける**：一つだけ再確認するか、次の作業へ進むかを尋ね、また返答を待つ。

質問、説明、冗談、動作候補はLLMがその都度生成する。沈黙や聞き取り失敗を正解扱いにせず、新人の返答をR1自身で作らない。技術質問へ話題が移れば、コードの事実に基づく説明へ切り替える。

腕のプリセットで対象を示すことは、実際のボタン押下や荷物運搬を実装した意味ではない。歩行を含む見本は、そのセッションと接続先についてプログラムが許可した範囲に従う。新人の模擬操作や結果は人の申告として受け取り、R1がカメラで確認したことにはしない。

パネルの「説明と見本から研修を開始」、または「研修を始めて」で開始する。通話を開始してから研修開始ボタンを押すと、説明と見本が終わった後、そのまま声で答えられる。文字で答えることもできる。身ぶりがオフの場合は、オンにしてから開始する。

プログラムは説明→見本→一問の3段階を順に依頼し、各段階の動作候補と発話量を制限する。現在の仮想／ローカルの見本段階では短い前進を選べる。実機接続ではこの追加許可を使わず、腕の見本にする。新人の返答に応じた通常会話へ、見本用の歩行許可は持ち越さない。

「研修を中断」は発話と後続の段階を取り消す。通話終了や歩行停止も研修を中断する。会話リセット・研修資料変更で研修状態を解除し、応答先の切替では段階を保持する。LLMや動作が失敗した場合、実演で動作が選ばれなかった場合は次の質問へ進まず中断する。

LLMが発話と動作候補を同時に選び、プログラムが許可された動作・機体の状態・動作の重複・時間制限を確認する。架空の作業の創作と、実際の動作を実行してよいかの判断は別である。帽子の専用動作は未実装のまま扱う。

以前はPCの会話プレビューと仮想R1で構成を検討したが、現在は実機テストへ再開している。`--local` はPCでの会話・送信しない動作プレビューであり、仮想器のDDSサービスへ指令を送る経路とは区別する。

この資料を置くだけでは、起動済みパネルのコードや教材は自動更新されない。既存8770の旧プロセスへ新方針が反映されたとはみなさず、コード統合後の再起動・教材読込み・動作確認が必要である。

## 応答先と以前の固定再生

StrataとGPT APIは、同じ研修担当の人格・教材・会話を引き継いで手動で切り替える。応答先を変えても、上記3領域の基準は変えない。現在の起動引数と操作は、実際に統合されたコードで確認する。

`scripts/virtual_scenario.py` と `scenarios/presentation_v2.json` は、決めた組み合わせの順序や待ち合わせを再現する回帰試験用として残す。本番の即興対話を、その31段の固定再生で置き換えない。

世界設定や指示文の変更をLoRA学習済みとは説明しない。突然の日英切替とインドなまりの聞き取りは、実際の話者の音声を使う確認が別途必要である。

追加改修後は269件の単体・統合テストが通過。実GPTと仮想R1を使い、以下を確認した（`logs/training_flow_acceptance_20261115_071234.json`）。
